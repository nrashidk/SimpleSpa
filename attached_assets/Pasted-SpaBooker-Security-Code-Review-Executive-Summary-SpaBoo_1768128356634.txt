SpaBooker Security & Code Review
Executive Summary
SpaBooker is a well-architected multi-tenant booking platform with strong security fundamentals in place. The team has implemented enterprise-grade security controls including CSRF protection, rate limiting, audit logging with cryptographic integrity, and proper encryption for sensitive data. However, there are critical high-impact issues that need immediate attention, along with architectural improvements to support long-term scalability.

Overall Security Grade: B+ (Good with Critical Gaps)
Code Quality Grade: B (Solid but needs refactoring)

1. Security & Privacy (Critical Issues Only)
🔴 CRITICAL - High Risk
1.1 Stripe Webhook Secret Not Enforced (Payment Security)
Location: server/stripeWebhook.ts:16-21

Issue:

if (webhookSecret) {
  event = stripe.webhooks.constructEvent(payload, signature, webhookSecret);
} else {
  logger.warn('[Stripe Webhook] No webhook secret configured, parsing payload directly');
  event = JSON.parse(payload.toString());
}

Risk: Without signature verification, attackers can forge payment webhooks to:

Mark unpaid bookings as paid
Trigger fraudulent refunds
Manipulate booking status
Impact: Financial fraud, revenue loss, booking system compromise

Fix:

// REQUIRE webhook secret - fail hard if not configured
const webhookSecret = process.env.STRIPE_WEBHOOK_SECRET;
if (!webhookSecret) {
  throw new Error('STRIPE_WEBHOOK_SECRET is required for secure payment processing');
}
event = stripe.webhooks.constructEvent(payload, signature, webhookSecret);

Priority: IMMEDIATE - This is a financial security vulnerability

1.2 SQL Injection Risk via Template Literals
Location: server/storage.ts:413, 553, 561, 569, 577 and others

Issue:

.where(sql`LOWER(${users.email}) = ${normalizedEmail}`)

While Drizzle ORM provides parameterization, the use of sql template literals with interpolated values is inconsistent and could lead to SQL injection if developers aren't careful with string concatenation.

Risk: SQL injection if any code path allows unsanitized user input into sql templates

Safer Pattern:

// Use Drizzle's type-safe query builder instead
.where(eq(sql`LOWER(${users.email})`, normalizedEmail))
// Or better - add a generated column for lowercase email

Impact: Database compromise, data exfiltration, privilege escalation

Fix:

Add database-level generated columns for case-insensitive searches
Use Drizzle's query builder consistently
Add SQL injection tests to test suite
Priority: HIGH

1.3 OTP Storage in Memory (Authentication Bypass)
Location: server/firebaseAuth.ts:331

Issue:

const otpStore = new Map<string, { otp: string; expiresAt: number; attempts: number }>();

Risk:

OTPs lost on server restart → users locked out
No distributed support → breaks in multi-instance deployments
No rate limiting per phone number across instances
Memory leak if cleanup fails
Impact:

Authentication failures in production
Horizontal scaling blocked
Potential DoS via OTP flooding
Fix:

// Use Redis or database table
CREATE TABLE otp_codes (
  phone VARCHAR(20) PRIMARY KEY,
  otp VARCHAR(6) NOT NULL,
  expires_at TIMESTAMP NOT NULL,
  attempts INT DEFAULT 0,
  created_at TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_otp_expires ON otp_codes(expires_at);

Priority: HIGH (blocks production scalability)

AUDIT_LOG_SECRET (defaults to ENCRYPTION_KEY, but should be separate)
CORS_ORIGIN (allows any origin in dev mode)

const productionEnvSchema = z.object({

  SMTP_HOST: z.string().min(1),
  SMTP_USER: z.string().min(1),
  SMTP_PASS: z.string().min(1),
});

1.6 Session Cookie Security in Production
Location: server/firebaseAuth.ts:45-50

Issue:

  httpOnly: true,  // ✅ Good
  secure: isProduction,  // ✅ Good
  maxAge: sessionTtl,
  sameSite: isProduction ? 'none' : 'lax',  // ⚠️ ISSUE
}

Risk: sameSite: 'none' in production allows CSRF attacks from third-party sites

Why it's there: Likely for cross-origin requests, but CSRF token should handle this

if (application && application.userId !== req.user.claims.sub) {

Issue:

setInterval(() => {
  const now = Date.now();
  for (const [nonce, expiry] of usedOAuthNonces.entries()) {
    if (now > expiry) {
      usedOAuthNonces.delete(nonce);
    }
  }
}, 5 * 60 * 1000);

Risk:

2.4 No Caching Strategy
Issue:

Spa settings fetched on every request
Service catalog queried repeatedly
Staff schedules not cached
No Redis/Memcached layer
Impact:

High database load
Slow response times
Cannot scale horizontally
Fix:

import Redis from 'ioredis';
const redis = new Redis(process.env.REDIS_URL);

// Cache spa settings
export async function getSpaSettings(spaId: number) {
  const cached = await redis.get(`spa:${spaId}:settings`);
  if (cached) return JSON.parse(cached);
  
  const settings = await db.select()...;
  await redis.setex(`spa:${spaId}:settings`, 3600, JSON.stringify(settings));
  return settings;
}
